# TwinDock: warehouse digital twin on Silicon Labs SiWx917

This file is the standing brief for every task in this repo. Read it fully before starting any work.

## What we are building

A browser-based digital twin of a small warehouse ("Riverside Logistics Hub"), shown as an
isometric, low-poly 3D world with an operations HUD on top. It has three inputs:

1. **The physical SiWx917 board** (real firmware, real data). Its buttons, LEDs, Wi-Fi state and
   BLE scans are mirrored in the twin, and the twin can command it (LED control).
2. **The Control Room page**, where an operator manually moves forklifts and trucks.
   Every move appears in the 3D twin in real time, on every open screen.
3. **Optional auto mode** for background movement. Off by default.

The design language is inspired by Dilum Sanjaya's "WareTrack" concept (credit it in the README).
Do NOT copy its name, logo, wordmarks or truck branding. Our product name is **TwinDock**.

## Non-negotiable data rules

- **The board is never faked.** Every value shown for the gateway/board (button state, LED state,
  Wi-Fi RSSI, uptime, message counters, BLE sightings, any onboard sensor) must come from a real
  MQTT message sent by the firmware. If no message has arrived, show "Waiting for device" or the
  last value greyed out with its age ("12s ago"). Never generate, interpolate or default a board value.
- **Only expose hardware that exists.** The board twin may only show LEDs, buttons and sensors listed
  in `HARDWARE.md`, which is built from the board's user guide and SDK board config, and confirmed
  by the developer.
- **Every unit has a `source` field:** `"device"`, `"manual"` or `"auto"`. The UI shows device units
  with the violet LIVE badge. Nothing pretends to be device data.
- **The backend is the single source of truth.** Clients send intents; the backend validates,
  updates world state, and broadcasts. Clients never move units locally without the server.

## MQTT contract

`/shared/schemas` is authoritative and `/shared/schema.md` explains it. This section is a summary
and must always match it; change `/shared` first, then this file, in the same commit.

| Topic | Direction | Payload |
|---|---|---|
| `twin/gateway/status` | board → | `{ts_ms, uptime_s, wifi_rssi_dbm, wifi_connected, ip, fw_version, msgs_sent, reconnects, buffered, replay}` every 5 s. Only `ts_ms` is required; fields the SDK can't give are omitted. Messages flushed from the offline buffer keep their original `ts_ms` and set `replay: true` |
| `twin/gateway/button` | board → | `{ts_ms, button: "BTN0", state: "pressed" \| "released"}` on change |
| `twin/gateway/led` | board → | `{ts_ms, led: "LED0", on: true, cmd_id?}` on change (confirmation, not command); `cmd_id` echoes the command that caused it |
| `twin/gateway/ble` | board → | `{ts_ms, sightings: [{name, addr, rssi_dbm}]}` every 2 s, filtered to names starting `TD-` |
| `twin/gateway/sensor/<name>` | board → | `{ts_ms, value, unit}` only for sensors in HARDWARE.md |
| `twin/gateway/cmd/led` | → board | `{led: "LED0", on: true, cmd_id}` (`cmd_id` ≤ 36 chars, generated by the backend) |
| `twin/gateway/hello` | board → | retained; `{board, radio_board, fw_version, leds[], buttons[], sensors[]}` |

The LED in the UI turns on only after the board's confirmation on `twin/gateway/led` arrives,
not when the user clicks. Show a short pending state in between.

## WebSocket contract (`/ws`)

Every message has a `type`. Server → client: `world_snapshot` (on connect and after reset),
`unit_update` (changed units, ≤ 20 Hz), `gateway_update` (after each device message, with the
`raw` MQTT message), `selection_changed`, `command_ack` (`ok`, `reason`, planned `path`),
`event` (`{seq, server_ts_ms, level: info|warn|error, source, text, unit_id?}` for the event log:
BTN0/BTN1 actions, auto mode, LED timeouts, dropped device messages, BLE tags), and
`ble_tracks` (after each BLE scan: per tag last/smoothed RSSI, raw/committed/pending zone, plus
the zone config), `sim_clock` (simulated time, speed ×1/×5/×20,
warm start; every `server_ts_ms` is on this clock), `control_update` (work orders, recommendations waiting for
a person, the cause → action → result log of automatic actions), `logistics_update` (logistics KPIs, truck
stages and weighbridge tickets, orders, inventory, forklift batteries in Ah).
Client → server: `move_unit` (`unit_id`, `target_node`, `action`, `dry_run`, optional `pallet_id`
for `pick`), `select_unit` (a unit or a device id), `led_command`, `set_auto_mode`, `set_sim_speed`
(refused above ×1 while the real board is online), `control_decision` (approve or dismiss a recommendation:
anything that stops production or calls emergency services waits for a person).

Site twin additions (see `shared/schema.md`): server → client `device_update`,
`production_update`, `safety_update`, `alerts_update` (and `sites` + `devices` in `world_snapshot`);
client → server `machine_command`, `ack_alert`, `scenario_command`, `safety_command` (evacuation, close SOS/man-down, simulated-badge demo actions). MQTT: simulated devices on
`twin/<site>/<device>/<channel>` (`mqtt/site_hello|status|reading.json`, `source` always `"sim"`),
simulator commands on `twin/<site>/<device>/cmd/<action>` (`mqtt/site_cmd.json`).

Units carry, besides position, state and `source`: `plan` (forklifts: queued `{node, action}`
steps; BTN0 runs the first), `holder` (pallets: the forklift or truck holding it), `cargo`
(trucks: pallet ids on board), `carrying`, `docked_at`, `battery_pct`, `task`, `meta`.

## World model

The floor is a coordinate grid in meters (origin at the warehouse's north-west corner, x east,
z south). Movement happens along a **waypoint graph** defined in `backend/world/layout.json`:
named nodes (`DOCK_1`, `RACK_A3`, `CHARGER_C1`, `ZONE_B`, `GATE_IN`...) and lanes between them.
Units move along shortest paths at realistic speeds (forklift 2.2 m/s, truck in yard 3 m/s),
with heading following the path, played 2.5× faster for the demo (`PACE` in `world.py`,
`TWINDOCK_PACE=1` for real speed).

Entities: `forklift`, `truck`, `pallet`, `dock`, `rack`, `charger`, `gateway`.

Forklift states: `idle`, `driving`, `picking`, `carrying`, `loading`, `charging`.
Truck states: `arriving`, `docked`, `loading`, `departing`, `gone`.
Dock states: `available`, `occupied`, `maintenance`.

Physical controls (exact mapping finalised after HARDWARE.md):
- BTN0 short press: selected forklift drives to its next waypoint in its task list.
- BTN1 short press: select next forklift (selection is shared across all clients).
- LED0 on while any truck is docked at Bay 1. LED1 controlled manually from the twin.
- BRD2605A has one RGB LED: LED0 = its green channel, LED1 = its blue channel (see HARDWARE.md).
  The board twin shows a single LED whose colour is the mix.

## Visual design spec

**Feel:** a clean, bright, premium strategy-game world with an enterprise HUD floating over it.
Calm, airy, never cartoonish. The 3D scene fills the whole viewport; HUD cards float on top.

**Palette (tokens in `frontend/src/theme.ts` and CSS variables):**
Silicon Labs theme: red #D91E2A and black, on neutral greys. No blue anywhere (except the board's
real blue LED channel). Logo: `frontend/public/brand/silicon-labs.png`, shown next to the TwinDock name.
Exception: on `/wiring`, wires are drawn in their real physical colours (Qwiic red 3.3 V, black GND,
blue SDA, yellow SCL; load-cell wires red/black/white/green), including blue. Nothing else on that
page may use them.
- `--ground` #EDEDED neutral grey floor; `--road` #DEDEDE with white dashed lane markings
- `--structure` #D91E2A warehouse walls/roofs; `--structure-dark` #A8141F roof shading
- `--accent` #D91E2A: selection brackets, map pins, routes, hover, primary buttons, shipment stepper
- `--card` #FFFFFF at 96% opacity, 1px border #E6E6E6, shadow `0 8px 24px rgba(0,0,0,0.08)`
- `--ink` #111111 primary text; `--ink-2` #6B6B6B secondary text
- `--ok` #16A34A (pill bg #E8F7EE); `--info` #111111 (bg #EFEFEF), black so in-progress pills never read
  as alarms; `--warn` #D97706 (bg #FFF4E0); `--crit` #DC2626 (bg #FDECEC); `--idle` #8C8C8C (bg #F2F2F2)
- `--live` #7C3AED: reserved exclusively for real board/device data (LIVE badges, gateway range ring)
- Floor markings yellow #F2C230; cardboard boxes #D9B48A / #C79A6B; pallets #B98A5A; trees #6BBF8A

**Type:** "Inter" (fallback system-ui). Sizes 12 / 13 / 15 / 20 / 28. KPI numbers 28 semibold
with tabular numerals; labels 13 regular `--ink-2`. Sentence case everywhere.

**3D scene:**
- Orthographic camera, isometric angle (~35° elevation, 45° yaw). Zoom limited 0.6x–2x.
  Pan with drag; rotate in 90° steps via the map controls only.
- All models built procedurally from primitives (boxes, cylinders, rounded boxes) in a
  consistent low-poly style: warehouse with ribbed red roof and roll-up dock doors labelled
  D1–D3, racks with cardboard pallets, forklifts (yellow body, black mast, small driver),

  Target 60 fps on a mid-range laptop; use instancing for boxes and pallets.
- Selected unit: red corner-bracket frame on the ground around it, plus a floating pill label
  above it ("FL-01 · Loading truck"). Hovered unit: subtle outline.
- Map pins (red teardrop) mark points of interest such as the active pallet's destination.
- The gateway (board) stands on a pole near the docks with a faint violet BLE range ring.

## Site twin

TwinDock also models a **site**: WH-01 (the warehouse) and FAC-01 "Riverside Assembly" (a factory
east of it, same metre grid and waypoint graph). Sites, zones and commissioned devices are in
`backend/world/sites.json`; geometry stays in `backend/world/layout.json`. Plan: `docs/site_plan.md`.

- **Every device shows LIVE (violet) or SIM (grey) everywhere it appears.** GW-01, the real
  SiWx917, is the only LIVE device. Everything from `tools/site_sim.py` is SIM.
- **Simulated devices never write into real device state and never trigger real LED or board
  commands.** Sim devices publish on `twin/<site>/<device>/<channel>` (schemas `mqtt/site_*.json`,
  `source` is the constant `"sim"`). The backend routes `twin/gateway/*` to the board code and
  everything else to the device registry (`backend/twindock/devices.py`), which has no path to the
  gateway store, LEDs or MQTT output. A site-topic message naming a real device (GW-01) is
  dropped. GW-01's device entry is derived from the board's own messages only.
  `tests/test_sites.py::test_sim_messages_never_touch_the_real_board` must always pass.
- **No value is shown without a source and an age.** Device readings carry `received_ms`; the UI
  shows "12s ago" next to them.
- **Device protocols are labelled honestly**: a simulated Thread device is "SIM · Thread", the
  board is "LIVE · Wi-Fi".
- Device status: online (last message ≤ 15 s, same as the board), stale (≤ 60 s), offline (older or
  never), fault (the device reports one).
- Never change `firmware/`, the board's topics or GW-01's behaviour for site-twin work.
- With no broker (hosted deploy), the backend runs `tools/site_sim.py` in-process (`backend/twindock/embedded_sim.py`,
  `TWINDOCK_SIM=auto|embedded|external`): same topics and schemas, into the device registry only, never the board.

## Coding conventions

- TypeScript strict mode; no `any`. Python 3.11 with type hints and pydantic models.
- Every message type is defined once in `/shared` and validated on both ends.
- Firmware in C following the SDK example structure; no dynamic allocation in hot paths;
  comment every non-obvious choice (scan interval, publish rate, buffer size) with the reason.
- Small commits with clear messages after each working step.
- When something is uncertain about the hardware or SDK, stop and ask instead of guessing.

## Device kits

`hardware/kits/<kit_id>.json` (schema `shared/schemas/hardware/wiring.json`) describes one asset's
sensor pack. Only `fl01_sensor_pack` (SiWx917 BRD2605A) is **built**; every other kit is a
**reference design** (real, buyable parts, correct wiring, simulated data with `source: "sim"`).
Wiring pages show "Built and verified" or "Simulated kit" (the UI never says "reference"; simulated kits show their SIM devices' readings). Pages: `/kits`, `/wiring/:kit_id`.
Silicon Labs radios first (SiWx917 for mains/vehicle Wi-Fi, EFR32BG for coin-cell BLE, EFR32MG24 for
Thread/Matter/Zigbee); anything unconfirmed is `unverified`. Plan: `docs/kits_plan.md`.

## Riverside Campus

WH-01 (x −14…83) and FAC-01 (x 84…216) are one campus: gate and weighbridge, car park with EV chargers, admin block, canteen, medical room,
raw material store, manufacturing hall (2 lines), QC lab, maintenance workshop, utilities (substation, generator, compressor room, water tanks,
ETP), hazardous materials store, fire pump house, hydrants, muster points, rooftop solar. Plan with ASCII map: `docs/campus_plan.md`; generated by
`tools/campus/gen_campus.py` into `layout.json` (`campus` section, walkway and road nodes) and `sites.json` (zones with hazard and PPE, devices, workers).
Pedestrian nodes have `kinds: []`; walkways cross vehicle roads and lanes only on lanes marked `crossing` (tests in `tests/test_campus.py`).
